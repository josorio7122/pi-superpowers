# pi-superpowers v5.1.2 — Bugfix Design

**Date:** 2026-04-18
**Status:** Approved for planning
**Found in:** Real-world session in `yes-chef-impl` (see `/Users/josorio/.pi/agent/sessions/...2026-04-18T19-29-13-294Z_019da211-904e-73d3-885e-14a8dacd07d9.jsonl`)

## 1. Purpose

Three real bugs found during first real usage. Ship as `v5.1.2` patch release.

## 2. Bugs and fixes

### Bug 1 — `reconstructTodos` reads the wrong field

**Symptom:** Every `superpowers_todo` action other than the first `replace` returns an empty list. Every `complete`/`update`/`remove` silently resets state. Observable in the session log: 5 tool calls, `complete` actions always return `count: 0` despite prior populated state.

**Root cause:** pi's `sessionManager.getEntries()` returns `SessionEntry[]`. For tool results, the shape is:

```ts
type SessionMessageEntry = {
  type: "message";
  id: string;
  parentId: string | null;
  timestamp: string;
  message: {
    role: "toolResult";
    toolCallId: string;
    toolName: string;       // ← the field we need
    content: (TextContent | ImageContent)[];
    details?: TDetails;     // ← where our todos live
    isError: boolean;
    timestamp: number;
  };
};
```

My `reconstructTodos` in `src/todos/state.ts` checks `entry.tool` and `entry.details`. Neither field exists at the top level — both are one level deeper, under `.message`. My unit tests passed because the test mock used the wrong shape too. (Same mock-bug that masked the bootstrap-injection issue in v5.0.9.)

**Fix:**
- Update `SessionEntryLike` to model the real shape: `{ type?: string; message?: { role?: string; toolName?: string; details?: unknown } }`.
- `reconstructTodos` iterates entries, picks ones where `entry.message?.role === "toolResult" && entry.message?.toolName === "superpowers_todo"`, validates `entry.message.details` against `TodoDetailsSchema`, returns `details.todos`.
- Add a **regression test** that uses the real pi shape (fixtures built from the session log).
- Add an **E2E test** that actually exercises add → complete → list across 3 tool calls and asserts non-empty state survives.

### Bug 2 — No `general-purpose` default subagent; hallucinated role names

**Symptom:** Model tries to dispatch `backend-dev`, `implementer`, etc. via `superpowers_subagent` and gets "Unknown agent". Skills like `dispatching-parallel-agents` assume a generic worker exists.

**Root cause:** Upstream `obra/superpowers` ships only `agents/code-reviewer.md`. On Claude Code, unnamed dispatches use CC's built-in `general-purpose` subagent type; role-specific prompts (`implementer-prompt.md`, `spec-reviewer-prompt.md`) are **prompt templates the skills tell the model to read and pass as the task argument** — not registered agents. pi has no built-in generic, so unnamed dispatches fail.

**Fix — minimal, faithful to upstream:**
- **Add one pi-superpowers-authored built-in agent: `general-purpose`.** Register alongside upstream `agents/*.md`. Upstream-file agents take precedence on name collision. This gives pi parity with CC's default subagent slot.
- **Do NOT auto-register `*-prompt.md` templates.** Skills reference them as prompt templates — the model reads the file and passes its contents as the `task` argument to `superpowers_subagent` with `agent: "general-purpose"`. Same pattern as Claude Code.
- **`renderPiAddendum`** enumerates available names + explains the prompt-template pattern: *"Available agents: `code-reviewer`, `general-purpose`. For skill-specific workers (implementer, spec-reviewer, etc.), read the prompt template from the skill directory and pass it as `task` to `general-purpose`."*
- **Bootstrap injector** takes the agent list from `loadAgents()` and passes it to the addendum.

### Bug 2b — Pin bundled-agent model to `openai-codex/gpt-5.4`

User requirement: bundled agents run on `openai-codex/gpt-5.4`, not inherit the parent pi session's model.

**Fix:** In `agent-config-builder.resolveModel`, the fallback for `"inherit"` / missing upstream model becomes `"openai-codex/gpt-5.4"` (pinned default). Upstream agents with an explicit valid `provider/model` value still win. Env var `SUPERPOWERS_AGENT_MODEL` remains an escape hatch.

### Bug 3 — TUI inconsistency (symptom of Bug 1, with one small genuine fix)

**Symptom:** Screenshots show the panel going from 7 items → "no todos yet" → 3 items → no todos → 4 items. Feels jittery.

**Root cause:** 85% of this is Bug 1. When `complete` returns `[]`, the panel renders as empty. Fixing Bug 1 eliminates most of the jitter. The remaining 15%: the panel always re-renders on every tool call even when the result is empty, showing "(no todos yet)". After a failed `complete`, the model panics-re-adds items with fresh IDs, compounding confusion.

**Fix (small, targeted):**
- When a `complete`/`update`/`remove` action is called against a state that reconstructed empty (should be impossible after Bug 1 fix but still — a guard), **don't silently succeed with empty result**. Return a clear tool-error: *"Cannot apply 'complete' — no prior todos found in session."* This stops the model from invisibly losing state and gives it a legible error.
- Keep the widget-above-editor and in-message-panel double-surface as-is. With state reconstruction fixed, they'll agree. Cosmetic tightening of the widget/panel alignment is out of scope for v5.1.2.

## 3. Release

`v5.1.2`. No breaking changes. Pure correctness fixes.

## 4. TDD discipline (required per user request)

For each of the three fixes:

1. **Write the failing regression test first** — red.
2. **Implement minimum code to pass** — green.
3. **Verify no existing test broke** — `npm run check`.
4. **Commit the test + code together** so the test always travels with the fix.

Additional: one E2E test that exercises the full add-then-complete-then-list cycle against real pi. This catches "wrong-mock" class of bugs (which is how we missed Bug 1 initially).

## 5. Non-goals

- Reworking the TUI surfaces (widget vs panel). Deferred to v5.2 if user still wants it.
- Adding new agents beyond what upstream ships as prompt templates. Pure discovery, not authoring.
- Supporting user-authored agent overrides. Deferred.
