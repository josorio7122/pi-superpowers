# v5.6 — Dynamic skill frontmatter for dispatched agents

## Problem

Agents dispatched via the `agent` tool (`pi-agents`' `createAgentTool`) cannot invoke Superpowers skills. When such an agent is told "invoke the `superpowers:test-driven-development` skill", it reports — correctly — that no skill tool is available in its environment.

### Why

- `pi-agents` loads skills **eagerly** from each agent's `skills:` frontmatter at `runAgent()` time: `loadSkillContents()` reads every declared path and `assembleSystemPrompt()` inlines the content into the system prompt. There is no runtime skill-loading tool in the dispatched-agent environment.
- `src/subagents/agent-config-builder.ts:83` currently declares only one skill:

  ```ts
  skills: [{ path: vendorUsingSuperpowersSkill(), when: "always" }],
  ```

- `using-superpowers` instructs the model to "Use the Skill tool" — but that tool exists only in the top-level pi session (as the `/skill:name` command). Dispatched agents have `read`, `write`, `edit`, `bash`, `grep`, `find`, `ls`, plus knowledge/conversation/submit — nothing else.

Result: dispatched agents silently fall back to ad-hoc behavior instead of the disciplined workflows the skills encode.

## Goal

Dispatched agents must see the full Superpowers skills corpus at invocation time, without requiring a new runtime tool in `pi-agents`.

## Approach

Populate each dispatched agent's `skills:` frontmatter **dynamically** from the filesystem at session start. The existing `pi-agents` eager-load path then inlines every listed skill into the system prompt. Because the list is generated from `vendor/superpowers/skills/*/SKILL.md` at runtime, it tracks upstream changes automatically — sync the vendor tree, restart pi, and new skills are visible in the next session.

### Non-goals

- User-level (`~/.claude/skills`) or project-level (`.claude/skills`) skill discovery.
- A runtime on-demand skill-loading tool (possible future follow-up).
- Changes to `pi-agents`.
- Top-level pi-session behavior — `/skill:name` command UX is unchanged.

### Accepted tradeoff

Every dispatched agent pays a fixed ~25–30k input tokens of skill baseline per invocation (14 SKILL.md files, ~115 KB total). Parallel dispatches multiply cost. This is the explicit cost of full semantic parity without introducing a new runtime tool. Documented in README troubleshooting.

## Lifecycle

The change slots into the existing `session_start` hook in `src/index.ts`:

1. User enters pi → `session_start` fires.
2. `buildAllAgentConfigs()` runs. **New step**: before the per-agent loop, call `scanVendorSkills()` once.
3. Each `buildAgentConfig(upstream, { sessionDir, skills })` emits `skills: [...N entries]` in the returned `AgentConfig` frontmatter.
4. `createAgentTool({ agents: configs, ... })` is registered with those configs baked in.
5. Session becomes interactive. User dispatches — frontmatter already complete.

The scan runs once per session. Configs are frozen after registration. Re-syncing vendor content during a live session does not take effect until the next pi restart.

## Architecture

### New module: `src/skills/scan.ts`

```ts
export type VendorSkill = {
  name: string;           // directory name, e.g. "writing-plans"
  path: string;           // absolute path to SKILL.md
  description: string;    // parsed from SKILL.md frontmatter `description:`
};

export type ScanResult = {
  skills: ReadonlyArray<VendorSkill>;
  diagnostics: ReadonlyArray<{ level: "error" | "warn"; filePath: string; message: string }>;
};

export async function scanVendorSkills(skillsDir?: string): Promise<ScanResult>;
```

Behavior:

- Default `skillsDir` is `vendorSkillsDir()` (resolves to `vendor/superpowers/skills`).
- Lists immediate subdirectories; for each, checks for `<subdir>/SKILL.md`.
- Parses YAML frontmatter to extract `name` and `description`. Falls back to directory name if `name:` is missing; `description` defaults to empty string if absent.
- Skips subdirectories without a `SKILL.md` (e.g., potential `skills/shared/` non-skill dirs).
- Returns skills sorted alphabetically by `name` (deterministic for snapshot tests).
- Returns `{ skills: [], diagnostics: [...] }` gracefully if the dir doesn't exist — same posture as `src/skills/discover.ts:15`.
- Per-file failures (malformed YAML, unreadable file) produce a diagnostic and skip — remaining skills still load.

Frontmatter parsing reuses the existing logic in `src/subagents/frontmatter.ts`. Extend or factor it as needed; do not introduce a second YAML parser.

### Wire-in: `src/subagents/build-all-configs.ts`

Before the per-agent loop:

```ts
const { skills, diagnostics: skillDiagnostics } = await scanVendorSkills();
diagnostics.push(...skillDiagnostics);
```

Pass `skills` down into each `buildAgentConfig(upstream, { sessionDir, skills })` call. One scan per session, shared across all agents.

### Change: `src/subagents/agent-config-builder.ts`

Extend `BuildCtx`:

```ts
export type BuildCtx = {
  sessionDir: string;
  skills: ReadonlyArray<VendorSkill>;
};
```

Replace the hard-coded `skills:` line:

```ts
skills: ctx.skills.map((s) => ({ path: s.path, when: s.description || "always" })),
```

The `when:` field is descriptive metadata only — `pi-agents` uses it as the subheading after the skill name (`### name (when)` in `prompt/assembly.ts:37`). Using the upstream `description:` gives dispatched agents the skill's own "use when" voice for free.

`using-superpowers` remains included (per user decision) — its own `<SUBAGENT-STOP>` block self-gates its content when read by a dispatched agent. Safety over token savings.

## Error handling

| Failure mode | Behavior |
|---|---|
| `vendor/superpowers/skills/` missing | `scanVendorSkills()` returns `{ skills: [], diagnostics: [warn] }`. `buildAllAgentConfigs` then falls back to a single-entry `[using-superpowers]` list (see below) so dispatched agents still validate and get the base methodology. Warn diagnostic bubbles to the console. |
| Scan returns 0 skills for any reason | Same fallback as above. |
| Individual SKILL.md unreadable or has bad YAML | Skip that skill, push error diagnostic. Other skills load normally. If every SKILL.md fails to parse, the fallback engages. |
| Empty `description:` | Use `"always"` as the `when:` fallback. |
| No `SKILL.md` under a subdirectory | Silently skip the subdirectory — it isn't a skill. |

**Why the fallback is required.** `pi-agents`' `AgentFrontmatterSchema` enforces `skills: z.array(SkillSchema).min(1)` (`node_modules/pi-agents/src/schema/frontmatter.ts:35`). A literal `skills: []` frontmatter fails `validateAgent` and the agent never registers. The fallback in `build-all-configs.ts` keeps dispatch working in dev-checkout scenarios (no vendor tree) and preserves the exact pre-v5.6 behavior (one `using-superpowers` entry).

**Diagnostic level remap.** `ScanDiagnostic.level` is `"error" | "warn"`; `pi-agents`' `DiscoveryDiagnostic.level` is `"error" | "warning"`. The translation happens in the explicit push loop inside `buildAllAgentConfigs`.

Diagnostics surface through the existing `console.error("[superpowers] agent validation ...")` channel in `src/index.ts:59`. Nothing throws through `session_start`.

## Testing

Unit tests (vitest), mirroring existing style in `src/skills/discover.test.ts` and `src/subagents/*.test.ts`:

- `src/skills/scan.test.ts`
  - Fixture directory with 3 skills → sorted output, correct name/path/description.
  - Fixture with malformed YAML → diagnostic, bad skill skipped, good skills still returned.
  - Missing directory → empty result, warn diagnostic.
  - Subdir without `SKILL.md` → silently skipped.
- `src/subagents/agent-config-builder.test.ts` (extend)
  - Given N scanned skills, resulting `AgentConfig.frontmatter.skills` has N entries with correct `path` and `when`.
- `src/subagents/build-all-configs.test.ts` (extend)
  - Scan is called once even when building N agents (shared result passed through).

E2E smoke — one real session that dispatches an agent, asserts the rendered system prompt contains headers for every vendored skill. Extends `src/skills/skill-broadcast-e2e.test.ts`.

Parity check — if `scripts/parity-check` enforces skill coverage for any reason, update it so dynamic scan remains authoritative.

## Risks

| Risk | Mitigation |
|---|---|
| ~25–30k token baseline per dispatch | Accepted tradeoff; documented in README troubleshooting + this spec. |
| Parallel dispatches multiply cost | Flag in docs. Future: optional on-demand Skill tool as v5.7+ follow-up. |
| Upstream skill file missing frontmatter | Diagnostic + skip; session keeps running. |
| Scan latency grows with corpus | 14 files today; re-measure if corpus exceeds ~50. Async readdir + per-file reads parallelized via `Promise.all`. |
| Non-skill directories appearing under `skills/` | Scanner only emits entries where `<subdir>/SKILL.md` exists; non-skills silently ignored. |

## Out of scope — future work

- On-demand skill-loading tool for dispatched agents (would require upstream `pi-agents` change to forward `customTools` through `createAgentTool`). Would let us preload a smaller "core" set and lazy-load the rest.
- User-level / project-level skill discovery for dispatched agents.
- Per-agent skill filtering (e.g., `code-reviewer` only needs a subset).
