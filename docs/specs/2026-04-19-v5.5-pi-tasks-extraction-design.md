# v5.5 — Extract pi-tasks + drop superpowers_ wrapping

**Date:** 2026-04-19
**Status:** Design
**Target release:** pi-tasks v0.1.0 + pi-superpowers v5.5.0

## Goal

Extract the task-tracking system into a standalone `pi-tasks` package and consume it raw from pi-superpowers. Drop the `superpowers_subagent` / `superpowers_todo` name wrapping so pi-agents' `agent` tool and pi-tasks' `task` tool register under their library names. Result: pi-superpowers becomes a focused skills adapter that wires two upstream packages (pi-agents + pi-tasks) plus the vendored `obra/superpowers` skills, agents, and commands.

## Motivation

1. **Reuse** — task tracking is a generic primitive (Claude Code ships TodoWrite as a first-class tool). Any pi extension authoring an orchestrator pattern benefits.
2. **Cleaner mental model** — pi-agents provides the `agent` tool; pi-tasks provides the `task` tool; pi-superpowers provides *skills*. Each package owns one concern.
3. **Library-native TUI** — pi-agents and pi-tasks render their own BorderedBox panels via `pi-tui`. Re-branding via `{ ...base, name: "superpowers_subagent" }` fights the pattern.
4. **Symmetry** — pi-agents already lives as its own package. Splitting tasks the same way is the obvious next step.

## pi-tasks v0.1.0 public API

### Data types (`schema.ts`)

```ts
export type TaskStatus = "pending" | "in_progress" | "completed";
export type TaskPriority = "low" | "medium" | "high";

export type Task = {
  id: string;
  content: string;             // imperative — "Build auth flow"
  status: TaskStatus;
  priority?: TaskPriority;
  activeForm?: string;         // present-continuous — "Building auth flow"
  startedAt?: number;          // ms epoch, auto-set on in_progress transition
};

export type TaskAction =
  | { action: "list" }
  | { action: "clear" }
  | { action: "replace"; items: Task[] }
  | { action: "add"; content: string; activeForm?: string; priority?: TaskPriority }
  | { action: "update"; id: string; content?: string; activeForm?: string; status?: TaskStatus; priority?: TaskPriority }
  | { action: "complete"; id: string }
  | { action: "remove"; id: string };

export type TaskDetails = { tasks: Task[]; action: string };

export const TaskSchema: TSchema;
export const TaskStatusSchema: TSchema;
export const TaskPrioritySchema: TSchema;
export const TaskActionSchema: TSchema;
export const TaskDetailsSchema: TSchema;
export const TaskToolParamsSchema: TSchema;  // flat object for OpenAI function-calling
```

### State (`state.ts`)

```ts
export type SessionEntryLike = {
  type?: string;
  message?: { role?: string; toolName?: string; details?: unknown };
  tool?: string;
  details?: unknown;
};

/** Pure. Given the current task list + an action + optional clock, returns the new list. */
export function applyAction(
  items: readonly Task[],
  action: TaskAction,
  now?: number,
): Task[];

/** Walks pi session entries backward and returns the latest task-tool result. */
export function reconstructTasks(entries: SessionEntryLike[], toolName: string): Task[];
```

### Tool factory (`tool.ts`) — the headline API

```ts
export type CreateTasksToolConfig = {
  name?: string;              // default: "task"
  label?: string;             // default: "Tasks"
  description?: string;       // default: CC-style TodoWrite discipline text (4 rules)
  brand?: string;             // widget header icon, default: "◆"
  headerPrefix?: string;      // widget header prefix when no task is in_progress, default: "Tasks"
};

export function createTasksTool(config?: CreateTasksToolConfig): ToolDefinition<typeof TaskToolParamsSchema>;
```

Internally the factory:
- Validates input via `TaskActionSchema`
- Uses `reconstructTasks(entries, config.name ?? "task")` to pull prior state from the pi session
- Runs `applyAction(prior, action)` to produce the new list
- Renders the tool-result panel via `renderTasksResult`
- Calls `ctx.ui.setWidget(config.name ?? "task", renderTasksWidget(...))` with brand + headerPrefix from config
- Returns `{ content, details: { tasks, action } }` matching `TaskDetailsSchema`

### Guardrail on mutating empty state

Same as our current `executeTodos` guard: `update` / `complete` / `remove` on an empty prior list returns `renderTasksError` explaining "no prior tasks in session — use 'add' or 'replace' first". Keeps the v5.1.2 bug-preventer intact.

## pi-superpowers v5.5.0 changes

### index.ts shape (final)

```ts
import { createAgentTool } from "pi-agents";
import { createTasksTool } from "pi-tasks";
import { buildInjectHandler } from "./bootstrap/inject.js";
import { buildCommandHandler } from "./commands/handler.js";
import { loadCommands } from "./commands/loader.js";
import { vendorRoot } from "./common/paths.js";
import { buildResourcesDiscoverHandler } from "./skills/discover.js";
import { buildAllAgentConfigs } from "./subagents/build-all-configs.js";
import { loadAgents } from "./subagents/loader.js";
import { clearSuperpowersStatus, setSuperpowersStatus } from "./ui/status.js";

type ExtensionAPI = { /* ... */ };

export default async function superpowersExtension(pi: ExtensionAPI): Promise<void> {
  const { agents } = await loadAgents();

  pi.on("before_agent_start", buildInjectHandler({
    subagentAvailable: true,
    availableAgents: agents.map((a) => a.name),
  }) as never);
  pi.on("resources_discover", buildResourcesDiscoverHandler() as never);

  const commands = await loadCommands(vendorRoot());
  for (const cmd of commands) {
    pi.registerCommand(cmd.name, {
      description: cmd.description,
      handler: buildCommandHandler(cmd) as never,
    });
  }

  pi.on("session_start", (async (_event, ctx) => {
    setSuperpowersStatus(ctx as never, { text: "Superpowers · v5.5.0 · 14 skills · tasks + agents" });
    setTimeout(() => clearSuperpowersStatus(ctx as never), 3000);
  }) as never);

  // Register pi-tasks' `task` tool RAW — with a 🦸 brand so the widget header reads `🦸 Tasks · …`.
  pi.registerTool(createTasksTool({ brand: "🦸" }));

  // Register pi-agents' `agent` tool RAW, once sessionDir is known.
  pi.on("session_start", (async (_event, ctx) => {
    const anyCtx = ctx as {
      cwd: string;
      sessionManager: { getSessionDir: () => string };
      modelRegistry: unknown;
    };
    const sessionDir = anyCtx.sessionManager.getSessionDir();
    const { configs, diagnostics } = await buildAllAgentConfigs({ agents, sessionDir });
    for (const d of diagnostics) {
      console.error(`[superpowers] agent validation ${d.level}: ${d.filePath}: ${d.message}`);
    }
    pi.registerTool(createAgentTool({
      agents: configs,
      modelRegistry: anyCtx.modelRegistry as never,
      cwd: anyCtx.cwd,
      sessionDir,
      conversationLogPath: `${sessionDir}/superpowers/dispatch.jsonl`,
    }));
  }) as never);
}
```

## Breaking changes (v5.5.0)

1. Tool name `superpowers_subagent` removed → now `agent`
2. Tool name `superpowers_todo` removed → now `task`
3. Pre-v5.5 session entries with `superpowers_todo` name won't reconstruct via `reconstructTasks(entries, "task")` — user sees empty task list on resume. Acceptable (they can `task({action:"list"})` to confirm, then `add`/`replace` to restart)
4. Any external script or extension importing from pi-superpowers/api for Todo* symbols will break — those symbols now live at pi-tasks

Upstream skill bodies unaffected (they say "TodoWrite" / "Task tool" — the bootstrap addendum's platform mapping translates to `task` / `agent` for pi).

## Parity-check interaction

Unchanged. Parity-check validates vendor/ vs registered skills/agents/commands. The tool name changes from `superpowers_*` to library-native don't affect parity because parity only cares about vendored surfaces (skills, agents, commands), not the tool wrapping.

## Self-review

**Scope check:** two packages, clear dependency order (pi-tasks → pi-superpowers), one breaking release. Single focused goal.

**Placeholder scan:** no TBDs. Every API signature is concrete. All file paths stated.

**Internal consistency:** all `Task*` type names match across schema/state/render/tool. `createTasksTool` config fields match the widget/result props. pi-superpowers' consumption matches the factory's advertised API.

**Type consistency (pi-tasks ↔ pi-superpowers):**
- `reconstructTasks(entries, "task")` in pi-tasks factory matches the tool name the factory registers by default.
- pi-superpowers passes `createTasksTool({ brand: "🦸" })` with no name override → uses `"task"`. Session entries will be saved under `toolName: "task"` and reconstruct correctly.
- `createAgentTool` already ships with `name: "agent"` in pi-agents; no override in v5.5 → tool shows as `agent`.

**Risk: pi-tui peer dep version mismatch.** pi-tasks peer-depends on `pi-tui`; pi-superpowers doesn't explicitly depend on pi-tui today. After v5.5 both packages depend on it through pi-tasks or pi-agents transitively. Keep pi-tui as a peer in pi-tasks to avoid pinning conflicts.

**Risk: session state loss on upgrade.** Users upgrading mid-session lose their todo list (tool name mismatch). Mitigation: call out in the v5.5.0 release notes. Since tasks are session-scoped anyway, impact is limited to the current session.
