# v5.4 — Subagent UX + Todo Discipline

**Date:** 2026-04-18
**Status:** Design
**Target release:** v5.4.0

## Goal

Close two user-visible UX gaps observed in real `superpowers_subagent` and `superpowers_todo` usage while preserving v5.3's upstream parity.

1. **Subagent panel is dead air.** During dispatch the tool call renders a bare `"Working..."` with no agent name, no task text, no elapsed time, no metrics. Cause: we ignore pi's `onUpdate` streaming channel.
2. **Todos skip `in_progress`.** The model jumps pending→completed without flipping through `in_progress` first, so the widget shows no live progress even while a task is being worked.

Escape-to-cancel is already wired (signal threads through); fixing #1 also makes the cancel affordance visible. Subagent skill access already matches Claude Code (subagents don't get Skill tool — skills preload via frontmatter, which we can opt into later). That's out of scope here.

## Architecture

### Subagent tool: adopt pi-agents' `createAgentTool` wholesale

pi-agents ships a ready-made tool factory (`node_modules/pi-agents/src/tool/agent-tool.ts:12`) that gives us for free everything we've been duplicating by hand:

- Emits `onUpdate` every animation frame (`withAnimation` at `agent-tool-execute.ts:17`) with `AgentResultDetails` so pi re-renders the panel live
- Shows a `BorderedBox` header with the agent's icon + colored name + model
- Renders per-agent "Working..." + live metrics (tokens, tools, cost, duration)
- Transitions to ✓ + full output + final stats on done, ✗ on error
- Honors the abort signal correctly (escape-to-cancel works visibly)
- Ships a tested `renderCall` and `renderResult` for both single and parallel modes

We currently re-implement ~300 LoC of this across `src/subagents/tool.ts` and `src/subagents/render.ts`, without the streaming. Replacing it wholesale removes the duplication and fixes the panel in one step.

Our `src/subagents/agent-config-builder.ts` already produces the full `PiAgentConfig` shape pi-agents needs. We shift when it runs: today we call `buildAgentConfig` lazily inside each `handleSingle`/`handleMulti`; after v5.4 we call it once at extension startup for every loaded agent, producing the `ReadonlyArray<AgentConfig>` `createAgentTool` expects.

The `superpowers_subagent` tool **name, parameter schema, and semantics stay the same.** Only the rendering and execution wiring change. Parallel mode is preserved via pi-agents' built-in `parallel` support. Chain mode was already removed in v5.3 — this doesn't bring it back.

### Todo tool: rewrite the description

The `superpowers_todo` tool description at `src/index.ts:75-76` currently reads:

> "Track session-scoped todos. Actions: add, replace, update, complete, remove, clear, list. See the action param schema for the shape each action expects."

That's neutral about *when* to use each action. Claude Code's TodoWrite manual (which pi doesn't replicate) explicitly teaches the flip-to-in_progress convention. Rewrite the description to bake that guidance into the tool itself, so the model reads it every call.

New description:

> "Track session-scoped todos. Actions: `add`, `replace`, `update`, `complete`, `remove`, `clear`, `list`.
>
> **Discipline (match Claude Code TodoWrite):**
> - Before starting work on a task, call `update` with `status: 'in_progress'`.
> - Only ONE task may be `in_progress` at a time. Finish or park the current one before flipping another.
> - Call `complete` (or `update` with `status: 'completed'`) the moment a task is finished — don't batch.
> - Break large tasks into smaller sub-tasks if you can't commit to finishing in one go."

No validation, no blocking — matches upstream's "instruct, don't gate" philosophy. If discipline still doesn't land, add validation in a follow-up.

## Error handling

- Unknown agent name → already handled by `createAgentTool` with a clear error listing available agents; our tests lock that behavior
- `modelRegistry` missing → pi guarantees it on the extension ctx; throw during init if absent so the failure is visible
- Abort signal → propagated by `createAgentTool`; escape in the pi TUI cancels cleanly

## Breaking changes

None at the API surface. The tool name, parameter shape (`{agent, task}` or `{tasks}`), and result envelope stay the same. Only the **visual rendering** changes — panels are now BorderedBox style (pi-agents native) instead of our `●`/`⎿` tree. Todos and all other UI are untouched.

## Testing approach

- **Unit:** `build-all-configs.test.ts` for the eager config builder (covers empty list, happy path, model override)
- **Integration:** `createAgentTool-integration.test.ts` registers the tool against a stub pi API and asserts the typebox schema accepts both modes
- **E2E:** one retained E2E test hitting `pi -p` with a real single-dispatch call that checks the tool result contains the subagent's output and at least one `runningEntry` was emitted (via marker or captured `onUpdate`)
- **Parity:** `npm run parity-check` must stay green — no vendor surface changes

## Out of scope (follow-ups)

- Populating `skills: [...]` in `buildAgentConfig` to preload superpowers skills into subagent startup context. Rationale: Claude Code subagents don't get Skill tool access either; skill preload is opt-in via frontmatter and upstream's vendored `code-reviewer.md` doesn't opt in. Closing this gap would be a deliberate deviation — separate design.
- Todo-discipline validation (soft warning when `complete` fires on a task never flipped to `in_progress`). Start description-only; add validation only if the flip rate stays low after v5.4.
- Migration of todo widget rendering to pi-agents' BorderedBox (keep tree style for now — no UX complaint and the simulator depends on it).
- Adopting pi-agents' `renderConversation` for cross-agent spans (only relevant once we chain or nest dispatches; chain is removed, nesting is unused).
